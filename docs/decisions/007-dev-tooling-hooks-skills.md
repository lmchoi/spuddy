# ADR 007 — Dev Tooling: Hooks & Skills over CLAUDE.md Prose

**Status:** draft (under refinement)  
**Date:** 2026-05-24

---

## Context

Usage analysis across 75 sessions surfaced three recurring failure patterns:

1. **Premature "done" claims** — Claude commits or declares work finished without running builds or launching the app.
2. **Surface-level fixes** — First fix addresses the symptom; root cause requires multiple rounds to surface.
3. **Git state confusion** — Destructive operations, unintended changes pulled in during merges, wrong ahead/behind reads.

The current mitigation is CLAUDE.md prose (instructions like "run tests before committing"). This is unreliable — Claude follows it inconsistently and there's no enforcement mechanism.

---

## Decision

**Replace prose instructions with mechanical enforcement: hooks that block bad actions, skills that encode correct workflows.**

Specifically:

### Gate structure

Three distinct quality gates, each calling shared `package.json` scripts (single source of truth):

| Gate | Script | Checks | Approx time |
|---|---|---|---|
| `pre-commit` | `npm run check` | typecheck + tests | ~15–20s |
| `pre-push` | `npm run check:full` | typecheck + lint + tests + visual (if UI changed) | ~30–60s |
| CI | `npm run check:full` + bundle | everything | unbounded |

Lint is excluded from pre-commit (stylistic, not a correctness signal; slows the commit loop).  
`npm ci` and Expo bundle are excluded from all local hooks (too slow; CI is the right gate).

**Visual verification** runs at pre-push, not pre-commit — startup cost (~30s+) is too high for every commit. It runs selectively: only when staged changes include UI files (`.tsx` components outside `__tests__/`). Checks: app boots without crash, no console errors/warnings, screenshot diff against baseline. Implementation TBD — likely Detox or a lightweight Expo-specific approach.

### TDD enforcement

Two layers:

1. **pre-commit hook** (mechanical) — if source `.ts`/`.tsx` files are staged, test files must also be staged. Whitelisted paths that legitimately have no tests: `types/`, `constants/`, `*.config.*`, `jest.setup.*`. Blocks the commit with a clear message if violated.

2. **`/sp:implement` skill** (workflow) — entry point for any new feature. Drives the red→green→commit sequence explicitly. The hook is the safety net; the skill is the guide.

Temporal ordering (test written *before* implementation) cannot be enforced mechanically by git — git sees state, not history. The skill handles this by making the sequence explicit.

### Permission allowlist

Common read-only and mechanical Bash operations are pre-approved in `.claude/settings.json` so Claude never pauses mid-workflow to ask permission for routine commands. Generated by scanning session transcripts via `/fewer-permission-prompts`. This is a prerequisite for autonomous skill execution — without it, skills get interrupted before they can do useful work.

### Destructive command guard

A `PreToolUse` hook on `Bash` blocks patterns that have caused data loss in prior sessions:
- `cp -r` into an existing git repo
- `git reset --hard`, `git checkout --`, `git clean -f`
- `rm -rf` on non-temporary paths

Hook outputs a clear error and stops. Claude must use git-aware alternatives or ask explicitly. Overridable only by the user, not by Claude.

### Custom skills

Stored at project level (`.claude/skills/`), prefixed `sp:` to distinguish from system skills and built-ins. Each skill file includes a `model:` frontmatter — haiku for mechanical setup, sonnet for reasoning-heavy work.

| Skill | Model | Purpose |
|---|---|---|
| `/sp:refine` | sonnet | Structured conversation → resolves open questions → writes plan |
| `/sp:start` | haiku | Creates worktree + branch, symlinks node_modules/.env — guards on plan existing |
| `/sp:implement` | sonnet | Orient → TDD loop → commit — guards on worktree existing |
| `/sp:fix` | sonnet | Bug-specific: regression test → fix → commit |
| `/sp:commit` | sonnet | Atomic commit hygiene — verify, check for unrelated changes, write message |
| `/sp:push` | sonnet | Docs check, check:full (+ visual), fix loop, push, open PR |
| `/sp:done` | haiku | Verify merged via gh CLI, clean up worktree and branch |
| `/sp:review` | sonnet | Superset of `/review` — adds plan-adherence check and simplification pass |

A `SKILLS.md` in `.claude/skills/` serves as the index — one line per skill, what it does, when to use it vs the others.

### Known gap: root cause diagnosis

No mechanical enforcement exists for this. When a fix doesn't resolve an issue, Claude tends to layer patches rather than re-investigate. This is a reasoning failure, not a workflow failure. Partial mitigation: `/sp:fix` explicitly requires stating the root cause hypothesis before editing any file. Full mitigation requires model improvement, not tooling.

## Proposed workflows for common tasks

### Starting a new feature slice

```
/sp:refine <description>    → phase-by-phase conversation:
                              1. restate + confirm understanding
                              2. split check — can this ship as two independent pieces?
                              3. testability check — how do we know it works?
                              4. value/alignment check — simpler version possible?
                              5. design discussion + flag hard-to-reverse decisions → ADR
                              6. commit breakdown — numbered atomic commits
                              outputs: docs/plans/<slug>.md

/sp:start <slug>            → guards: plan file must exist
                              1. git worktree add .claude/worktrees/<slug> -b feat/<slug>
                              2. symlink node_modules and .env from main tree
                              outputs: worktree path + branch name

/sp:implement               → guards: worktree must exist
                              1. read plan from docs/plans/, read existing code in areas to touch
                              2. follow existing patterns — do not invent new ones
                              3. for each commit in the plan:
                                 a. write failing test, confirm red
                                 b. implement until green
                                 c. /sp:commit
```

### Fixing a bug

```
/sp:fix <description>       → 1. state root cause hypothesis before touching any file
                              2. git worktree add .claude/worktrees/fix-<slug> -b fix/<slug>
                              3. symlink node_modules and .env from main tree
                              4. write regression test, confirm red
                              5. fix, confirm green
                              6. /sp:commit
```

### Committing any change

```
/sp:commit                  → shows staged diff, flags unrelated changes,
                              runs npm run check, writes conventional message
                              (pre-commit hook is final gate — test+source together)
```

### Pushing to remote

```
/sp:push                    → 1. check docs/plans/: are completed steps marked? deviations noted?
                              2. check if any significant decision needs an ADR
                              3. update docs and commit (separate atomic commit) if anything missing
                              4. run check:full (typecheck + lint + tests + visual if UI changed)
                              5. if failures: Claude diagnoses and fixes autonomously (up to retry limit)
                              6. push branch, open PR — record PR number
```

### After PR is merged

```
/sp:done                    → 1. run: gh pr view <branch> --json state — confirm MERGED before proceeding
                              2. git worktree remove .claude/worktrees/<slug>
                              3. delete local branch
                              (purely cleanup — docs were committed as part of /sp:push)
```

### Code review

```
/sp:review                  → runs the base /review logic, then adds:
                              1. plan-adherence check (does this match docs/plans/?)
                              2. simplification pass (anything over-engineered?)
```

## What this does NOT change

- CLAUDE.md remains the place for project context, doc structure, and workflow rules that can't be mechanically enforced (e.g. "write an ADR for significant decisions").
- The pre-push hook already exists and works. It will be updated to call `npm run check:full` (+ selective visual check) instead of inline commands.
- `/next-plan` is unchanged. `/sp:implement` reads the active plan but does not replace the planning step.
- The built-in `/review` skill is not modified — `/sp:review` is additive.
- The stop-hook reminder ("update docs/plans and PRD") is superseded by `/sp:push`, which commits doc updates before pushing — not a reminder, a mandatory step.

---

## Consequences

- Claude physically cannot commit unverified code (hook blocks it).
- Claude physically cannot commit source changes without tests (hook blocks it).
- Claude physically cannot run destructive shell commands without the user overriding (Bash hook blocks it).
- Permission allowlist eliminates mid-workflow interruptions for routine operations, enabling autonomous skill execution.
- Doc updates (plan, PRD, ADRs) are committed before pushing — not a reminder, a mandatory step.
- Worktrees keep feature work isolated from main; cleanup is explicit and intentional, not automatic.
- The workflow is self-documenting — new contributors (or future Claude sessions) can read the skills to understand how to work in this repo.
- **Remaining gap:** mid-session "step is done" claims before running the app are not mechanically blocked — only caught at pre-push by the visual check. Root cause misdiagnosis has no mechanical fix.
- Escape hatch: `--no-verify` for genuine edge cases. Should be rare and intentional.

## Open questions (to refine before implementing)

- Should `/sp:implement` read the active plan from `docs/plans/` automatically, or take a description as an argument?
- What exactly triggers the `PreToolUse` hook for the "write source without a test" safety net — `Edit` and `Write` on `.ts`/`.tsx` files? What does it check?
- Should the test-presence check in pre-commit look at staged files only, or also unstaged modifications in the working tree?
- How should whitelisted paths be maintained — hardcoded in the hook script, or in a config file?
- Visual verification approach: Detox, or a lighter Expo-specific tool? What constitutes a "visual test" at pre-push (screenshot diff, console errors, or both)?
- `/sp:push` autonomy boundary: how many fix-and-retry loops before it stops and asks?
- `/sp:review` plan-adherence check: does it read the most recently modified plan file, or should the user specify which plan?
- Worktree location: `.claude/worktrees/` (follows existing convention). Symlink `node_modules` and `.env` from main tree on creation to avoid reinstall cost.
- `/sp:done` is user-invoked; it verifies merge via `gh pr view --json state` before doing anything destructive.
- `/sp:push` doc-update step: does Claude propose plan/PRD diffs and wait for approval, or write and report?

# ADR-013: Adopt Drizzle ORM for database migrations and queries

## Context

`src/storage.ts` managed the SQLite schema via a `SCHEMA_STATEMENTS` array of raw `CREATE TABLE IF NOT EXISTS` strings run on every startup. There was no migration versioning — if the schema evolved, a hand-written `migrate()` function checked `PRAGMA table_info` and reconstructed tables manually.

As the schema stabilises and new columns or tables become likely, this approach requires writing migration SQL by hand, which is error-prone and leaves no reviewable history of what changed and when.

Two alternatives were evaluated:

- **Raw `PRAGMA user_version`** — increment a version integer and run hand-written SQL blocks keyed on version. Simple but still requires writing migration SQL by hand; no tooling to generate diffs.
- **Drizzle ORM with drizzle-kit** — define schema as TypeScript table definitions; drizzle-kit generates reviewable `.sql` migration files from diffs. Provides a typed query builder as a bonus.

## Decision

Adopt `drizzle-orm` (runtime) and `drizzle-kit` (dev, migration CLI).

- Schema is defined in `src/db/schema.ts` as Drizzle table definitions (the single source of truth going forward).
- Migrations are generated by `drizzle-kit generate` and stored as versioned `.sql` files in `drizzle/`. These files must never be hand-edited after applying.
- `initDB()` runs migrations via `drizzle-orm/expo-sqlite/migrator` on every startup; applied migrations are tracked by Drizzle in a `__drizzle_migrations` table, so they only run once.
- Tests use `drizzle-orm/better-sqlite3` with the same migration folder, giving identical schema in test and production.
- The old hand-written `DB` interface, `makeTestDB`, `initSchema`, and the `exercise_name → exercise_id` migration function are all removed. Because this is pre-public-release with no real users on the old schema, there is no data to migrate.
- Storage queries use the Drizzle typed query builder for writes (`insert`, `update`, `delete`) and the `db.all<T>(sql\`...\`)` approach for reads in synchronous contexts (transaction callbacks). Async reads use the awaitable select builder.

## Consequences

- **Reviewable history**: every future schema change produces a diff-able `.sql` file in `drizzle/`.
- **Type safety on writes**: TypeScript rejects inserts/updates that reference non-existent columns or mismatched types.
- **Generated files are the source of truth**: `drizzle/` files must not be hand-edited. A new migration requires running `drizzle-kit generate` after updating `src/db/schema.ts`.
- **Expo bundling**: the expo-sqlite migrator needs migrations bundled as an object (not read from disk). `src/db/migrations.ts` bundles the SQL strings; this file must be kept in sync with the `drizzle/` folder whenever a new migration is generated.
- **Sync/async split**: Drizzle's expo-sqlite adapter is `sync` mode, so database operations no longer throw "already released" errors; `getDB()` in `src/db.ts` is simplified accordingly.

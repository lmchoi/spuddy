# Plan: v0.2 — Program Import

**Status: closed** — implemented on `worktree-v0.2-program-import`, 2026-05-23.

## Goal

A user can import their program from a Liftosaur backup JSON, see the program's days and exercises in the app — ready for session logging in v0.3.

## What changed from the plan

**Multi-program support:** `parseProgramFromBackup` was refactored (during implementation) to return `Program[]` instead of a single `Program`. The backup JSON can contain multiple programs and all are imported. Storage and the import pipeline were updated to match (`savePrograms`, `getPrograms`).

**Active day selection removed from Settings:** The plan included a day selector for setting `active_day_index`. This was built and then removed — it's awkward UX to manage active day in Settings. Active day/program selection will be designed properly in v0.3 when session logging actually needs it. `updateActiveDayIndex` exists in the storage layer but is not exposed in the UI.

**`getProgramDay` made program-scoped:** Signature changed from `getProgramDay(db, dayIndex)` to `getProgramDay(db, programName, dayIndex)` to avoid ambiguity when multiple programs share the same day index.

**`savePrograms` wrapped in a transaction:** Flagged by code review (Gemini). A mid-import failure previously left the DB in a partial state.

**`fetch(uri)` for file reading:** `expo-file-system` is not installed. Using `fetch(uri)` instead, which works on iOS. Known gap for Android (`content://` URIs may be unreliable) — fix when Android testing begins.

## Design note — same exercise across days

If the same exercise appears on multiple days (e.g. Squat on Day 1 and Day 3), should progression be shared or tracked independently per day?

In real training these should share a single target — it's one exercise, not two. Liftosaur handles this via the exercise definition's progression state (not the `...` syntax). The `...` syntax is a different thing: a setup shortcut for different exercises that happen to start at the same weight, which will naturally diverge.

For v0.2, `program_exercises` rows are independent even if they share a name. The right place to solve this is the progression engine (v0.3) — likely by keying progression state on `exercise_name` rather than `program_exercise_id`. Captured here so the schema decision is made with this in mind, not retrofitted.

## Research findings

**Program location in backup JSON:** `programs[0].planner.weeks[].days[]`. The legacy `programs[0].days[]` array is empty in this backup — the planner format is what's in use.

**Day format:** Each day has `name` (e.g. "Day 1") and `exerciseText` — a multi-line text blob, same family as the session text format already parsed in `src/parser.ts`.

**exerciseText line types:**
- `// comment` — skip
- `Label: Exercise Name / ...` — strip the label prefix, parse the rest normally
- `Exercise Name / NxM-N / Nkg / progress: dp(...)` — exercise with sets, optional weight, optional progression config (ignore `progress:` field)
- `Exercise Name / ...OtherExercise` — "inherit sets from" reference. Resolved at import time across the whole program (two-pass: collect all exercise targets first, then resolve references). If the referenced exercise is not found anywhere in the program, targets default to empty. The inheritance relationship is not persisted — every exercise in Spuddy has independent targets that can be edited freely.
- `Exercise Name / 3x60` — reps-only (e.g. Plank — treat as time or reps, no weight target)
- `Exercise Name / 3x10+` — AMRAP (`+` suffix)

**Multi-week:** The fixture has one week. `isMultiweek: false`. Days are imported flat from `weeks[0].days[]` — if multiple weeks exist, import from `weeks[0]` only for now (simplest; can extend later).

**`nextDay` field:** `programs[0].nextDay` is an index into the flat day list — stored as `active_day_index` but not surfaced in the UI yet.

**Test fixture:** `__tests__/fixtures/liftosaur-backup.json` — real backup with 1 program, 3 days, cross-day `...` references.

## Carry-forward issues from v0.1

Two real issues surfaced during code review of the session history screens. Neither is blocking; defer to whichever milestone first touches these screens.

**1. ActivityStrip UTC/local mismatch** (`app/(tabs)/progress/index.tsx`)
`d.toISOString().slice(0, 10)` returns a UTC date string. In negative-UTC-offset timezones, this is one day behind local date near midnight, so a session logged today may not light up on today's dot. Fix: generate the date string from local year/month/day (`d.getFullYear()`, etc.) rather than ISO string.

**2. Palette duplicated across Colors.ts and progress screens**
`const C` in both progress screens repeats values already defined in `Colors.ts` (`background: '#08080E'`, `tint: '#39FF82'`). If the palette changes, both places need updating. Fix: export the extended palette from `Colors.ts` and import it rather than redeclaring inline.

## Steps

### 1. Walking skeleton — program domain wired end-to-end with stubs ✓

- Schema: `programs`, `program_days`, `program_exercises` tables added to `initSchema`
- Storage stubs: `saveProgram`, `getProgram`, `getProgramDay` — no-ops / return null
- Types: `Program`, `ProgramDay`, `ProgramExercise` added to `src/types.ts`

### 2. Planner exerciseText parser ✓

Pure function `parsePlannerDay(exerciseText: string): ProgramExercise[]`. Handles all line types. Two-pass reference resolution is done at the program level in `parseProgramFromBackup`.

### 3. Backup JSON program parser ✓

`parseProgramFromBackup(json: unknown): Program[] | ParseError`. Reads all programs from `programs[*].planner.weeks[0].days[]`. Returns error object on malformed input, never throws.

### 4. Program storage ✓

Real implementations of `savePrograms`, `getPrograms`, `getProgramDay`. Wrapped in a transaction. `getProgramDay` scoped by program name.

### 5. Settings — program import from file picker ✓

`importProgramFromJson(db, json)` pipeline. Settings screen: file picker → parse → save → show program name + day count or error.

### 6. Program day selector ✓ (partially)

Settings shows all programs as a read-only list of days with inline exercise names. Interactive day selection was removed — belongs in v0.3 session logging flow.
